# 自动采集规划：半自动采稀有药材

> 结论先行：主循环改为**看地图图标走**，不再以**坐标换算**为主。
> 追踪药材后，大地图上会显示药材图标；地图以角色为中心；采完的图标会消失。
> 这三件事合起来意味着：**地图本身就是状态**。屏幕上还看得见的，就是还没采的。
> 坐标库退居二线，只负责「视野里没图标时往哪拖」和事后统计。

---

## 0. 已拍板的决定（2026-09-27 追问结论）

| 问题 | 决定 | 对设计的影响 |
|---|---|---|
| 终极形态 | **半自动**：人在旁边看，一次跑一条路线 | 不做掉线重连、背包满之类的完整状态机；异常就暂停并提示 |
| 移动方式 | **纯 GUI 识途**，不用第三方传送工具 | 不碰游戏进程；慢一些、落点有偏差，这是接受的代价 |
| 识途目标 | 能点地图任意位置 | 点图标、点空白处都行 |
| 地图视野 | **以角色为中心**，要看远处得拖动 | 标定一次不能永久用 → 采用「以图标为准、现场定位」 |
| 地图药材 | **追踪后地图上有图标** | 目标直接从地图上认，不依赖坐标换算 |
| 采后图标 | **消失，刷新后再出现** | 不用自己维护已采清单和刷新计时 |
| 到点无 F 提示 | 小范围搜索，还没有就跳过 | 需要一个「就近搜索」动作 |
| 路线排序 | 近邻贪心 + 2-opt | 只在「视野外找下一片」时用得上 |
| 战斗 | 不处理（药材点基本没怪） | 不做战斗检测；靠卡住超时兜底 |
| 首批材料 | 高价值稀有药材（佛泪参 / 唐宫羽衣 / 恶相花 / 玉楼春 / 魏紫…） | 每种材料需要一张地图图标模板 |
| 验收 | **一条 20 点路线成功率 ≥ 70%** | 每个点都要记录结果，并生成报告 |
| 分工 | 云端写代码和探针，用户在 Windows 上跑并回传截图和日志 | 每个阶段先出 `probe_*.py`，拿到实测数据再写正式模块 |

### 风险声明（用户知情）

「不读内存、不注入进程」只能降低**客户端检测**的风险，**挡不住服务端行为检测**。
规律性的采集路线恰恰是行为检测的目标。缓解手段：`injector.Humanize` 随机延迟、
单次运行限时、人在旁边看。**不宣称零封号风险。**

### 随机化：每次不一样，但不指望靠它「隐身」

每一层都加随机，由一个 `--seed` 控制（默认取时间）。复现问题时传同一个 seed，就能重放同一次运行。

| 层 | 做法 | 落在哪 |
|---|---|---|
| 选下一个点 | 不总挑最近的：在最近的 3 个图标里按距离加权随机选（越近权重越大） | `harvest.pick_next` |
| 路线起点 / 方向 | 每次运行随机选起始图标；视野外找下一片时，2-opt 结果随机正走或反走 | `harvest` / `make_tasklist` |
| 点击位置 | 点图标、点【识途】都在目标框内高斯偏移，不点正中心 | 复用 `injector.Humanize` |
| 节奏 | 每步前后延迟都取区间；每 5~9 个点插一次 5~40 秒的「发呆」（原地转视角 / 开关背包） | `harvest.idle_break` |
| 跳点 | 约 10% 的概率跳过一个可采点（真人也会漏采） | `harvest.pick_next` |
| 就近搜索 | 转视角的方向、角度、步数都随机 | 阶段 3 策略函数 |
| 单次时长 | 路线上限在 15~35 分钟、12~25 点之间随机，跑完强制停 | `harvest` 启动参数 |

**要清楚的边界**：上面这些能消除「每次一模一样」的机械痕迹，
但行为检测更依赖**总量类统计**：每天采集时长、每小时产量、有没有连续几小时不停地采。
这些靠加随机藏不住，**真正有效的是控制总量**：单次限时、人在旁边看、别一天跑十几条路线。
这一条比任何随机都重要，风险仍然由用户自己承担。

测试上，随机化必须**可关闭、可复现**：`--seed 0 --no-jitter` 下行为完全确定，
离线测试都在这个模式下跑，另外单独测「同一 seed 两次结果相同、不同 seed 结果不同」。

## 1. 新主循环

```
          ┌──────────────────────────────────────────────┐
          ▼                                              │
  [1] 按 M 开地图 ── 确认地图已打开（模板：地图 UI 特征）       │
          │                                              │
  [2] 找图标：在地图画面里模板匹配已追踪的药材图标             │
          │   ├─ 有 → 最近 3 个里加权随机选一个              │
          │   └─ 没有 → [2b] 按坐标库方向拖地图 / 缩小一级再找  │
          │              还没有 → 本路线结束，出报告           │
  [3] 点图标 → 点【识途】（模板匹配按钮）                      │
          │                                              │
  [4] 等到达：帧差连续静止 N 次；超时 = stuck                  │
          │                                              │
  [5] 找 F 提示（屏幕中下部区域模板匹配）                      │
          │   ├─ 有 → 按 F → 确认提示消失 → ok               │
          │   └─ 没有 → [5b] 就近搜索（转视角 / 前后挪几步）    │
          │              还没有 → miss                      │
  [6] 记录本点结果（ok/miss/stuck + 耗时 + 截图） ─────────────┘
```

**为什么选离屏幕中心最近的**：地图以角色为中心，屏幕中心就是角色位置，
所以「最近图标」就是天然的近邻贪心，不需要知道角色的世界坐标。

**会卡住的地方和兜底**：

| 情况 | 检测 | 处理 |
|---|---|---|
| 识途遇水停下 | 静止但距离目标图标还很远（再开地图看图标是否仍在中心附近） | 重新点一次识途，最多 2 次，然后判 stuck |
| 识途被打断 | 同上 | 同上 |
| 同一图标反复失败 | 同一地图位置连续 miss 2 次 | 加进本轮黑名单（按地图相对位置 + 坐标库近邻判重） |
| 任意未知状态 | 连续 3 个点 stuck | **暂停 + 提示音**，等 F10 继续 |

## 2. 分阶段计划

每个阶段都是「先探针、再正式模块、最后测试」。
探针只做观测和截图，**不做任何连续操作**，由用户在游戏里手动运行并回传。

### 阶段 0：实测确认（只需探针，不写正式代码）

`rpa/probe_map.py`（已实现），分两段跑，产物在 `rpa/shots/probe_map/<时间戳>_auto|manual/`，结束时自动打包成同名 `.zip`，**把两个 zip 发回来**：

```bash
pip install -r requirements-dev.txt        # 只需 numpy；其余可选
python rpa/probe_map.py --selftest         # 先确认环境（不需要游戏）

# ① 自动（约 30 秒）：0.1 / 0.3 / 0.4 / 0.6。游戏窗口化或无边框，站在清河/开封野外
python rpa/probe_map.py auto

# ② 手动：按屏幕提示逐步操作，F9 截图 / F8 跳过 / F12 结束。覆盖 0.2 / 0.5 / 0.7 / 0.8
python rpa/probe_map.py manual
```

逐项内容：

| # | 要确认的事 | 探针动作 | 回传什么 |
|---|---|---|---|
| 0.1 | 地图打开的判据 | 按 M 前后各截一张 | 两张整屏截图 |
| 0.2 | 药材图标长什么样 | 追踪佛泪参后开地图截图 | 整屏截图（用来裁模板） |
| 0.3 | 地图缩放是否稳定 | 关开地图 3 次，每次截图 | 3 张图，比较界碑图标间距 |
| 0.4 | 角色是否真在屏幕中心 | 截图 + 标出屏幕中心 | 1 张标注图 |
| 0.5 | 【识途】按钮位置 | 手动点一个图标后截图 | 1 张图（用来裁按钮模板） |
| 0.6 | 拖动地图的手感 | 用 `injector` 发一次鼠标拖动，前后截图 | 两张图 + 拖动像素 vs 实际移动像素 |
| 0.7 | F 提示长什么样 | 人站在药材旁时截图 | 1 张图（用来裁 F 提示模板） |
| 0.8 | 识途落点偏差 | 人手动识途到 5 个药材点，每次到达后截图 | 5 张图：F 提示有没有出现 |

**0.8 最关键**：如果识途大多数时候直接停在 F 提示范围内，阶段 3 的就近搜索可以做得很简单；
如果普遍差几米，就近搜索就是成败的关键。

产出：`rpa/templates/`（地图UI、各药材图标、识途按钮、F 提示），以及一份实测记录追加到本文第 5 节。

### 阶段 1：地图图标识别 `rpa/mapview.py`

- `open_map()` / `close_map()`：按 M，用模板确认状态，不信返回值
- `find_icons(frame, templates) -> list[(kind, px, py, score)]`：多目标模板匹配 + 非极大值抑制
  （`vision.ncc_map` 目前只取最大值，需要扩展出「取所有峰值」）
- `nearest_to_center(icons)`
- **离线可测**：用阶段 0 的真实截图做测试夹具，断言识别出的图标数量和位置。
  这是整个项目第一批**基于真实游戏画面的回归测试**。

验收：阶段 0 截图里的图标，人工标注 vs 自动识别，召回率 ≥ 95%，误检 = 0。

### 阶段 2：单点闭环 `rpa/harvest.py`（第一版）

- 串起 [1]→[3]→[4]→[5]→[6]，**只跑一个点就退出**
- 复用：`injector`（发键、点击、聚焦、热键）、`vision.MotionDetector`（到达判定）、
  `gather.Detector`（F 提示）
- 每一步截图存证，写 `raw/rpa/<会话>/harvest.jsonl`
- `--dry-run`：只开地图、识别、打印要点哪里，不点

验收：同一个点连续手动触发 5 次，≥ 4 次成功采到。

### 阶段 3：就近搜索

按阶段 0.8 的结论二选一：

- **偏差小**：原地左右各转 90°，每转一次找一次 F 提示
- **偏差大**：重开地图，看目标图标是否还在、相对屏幕中心的方位 → 朝该方位走 1~2 秒 → 再找 F

两种都写成可配置的策略函数，方便后面对比成功率。

### 阶段 4：路线与报告

- 主循环跑到「视野里没有目标图标」为止
- [2b] 视野外找下一片：坐标库里该药材的点，按近邻贪心 + 2-opt 排好（复用 `make_tasklist.py`），
  决定往哪个方向拖地图。
  角色世界坐标未知 → 用**视野内已识别的界碑图标**反推（`mapnav` 的现场拟合），
  拿不到就退化为按固定螺旋顺序拖动搜索
- 限制：单次运行最长 N 分钟、最多 M 个点（默认 30 分钟 / 20 点）
- `tools/harvest_report.py`：读 `harvest.jsonl` → 成功率、每点耗时、miss/stuck 截图索引；
  WebUI「数据」页可以加一个采集记录板块（可选）

验收（**第一阶段完成的标志**）：**一条 20 点佛泪参路线，成功率 ≥ 70%**，报告可复现。

### 阶段 5（达标后再说）

- 扩到其他稀有药材：只需要加图标模板
- 挂机时长加长、加入更多拟人化
- 采集结果反哺坐标库：miss 多次的点标 `flag: field_missing`，走 ETL 进 WebUI

## 3. 对现有代码的处置

| 模块 | 处置 |
|---|---|
| `injector.py` | **原样复用**（扫描码、聚焦、热键已实测） |
| `vision.py` | 复用；`ncc_map` 之上加多峰值提取 |
| `gather.py` | 复用其中的 `Detector` 和 spot 逻辑；CLI 保留 |
| `navigate.py` | 其中的「点目的地 → 点识途 → 等静止」拆成函数给 `harvest.py` 用；「坐标换算后点击」降级为备用路径 |
| `mapnav.py` | 从主路径降级：只在 [2b] 用于现场拟合，推算角色位置 |
| `ocr.py` / `find_coords.py` | 暂不需要（游戏不显示坐标，已实测） |
| 影刀相关（`scripts/`、`collector.py`） | 不动 |

## 4. 明确不做的事

- 不读内存、不注入进程、不用第三方坐标传送工具
- 不做战斗处理、不做无人值守长时间挂机（第一阶段）
- 不追求 9 张图全覆盖：先把清河/开封的一种药材做到 70%
